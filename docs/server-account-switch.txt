已登录账号的服务端切换（PC JSK）

账号选择器中，本机恢复与服务端切换是两个动作。主动核对资格后，
当前账号不能作为切换目标；选择一个符合条件的其他账号，确认当前与
目标账号并同意协议后才发出切换请求。
当前与目标账号都需要独立的本机快速登录许可，且当前会话须取得官方 PC 分组；
本机恢复不依赖该许可。见 quick-login-offer-contracts.txt。


官方来源：PC 3.1.42.205594 M1368:4455–4482、9475–9520 的
JSK 选择、请求参数和路由；M290:196–285 同源 PC 请求适配；
M402:G 的 Web 回退带同源凭据。旧版 usableUserIds 和旧版请求体
不套到这个实现。
  先显式使用 /api/login/getquickloginlist 的同一原生历史选择；
  POST /api/login/switchuser（EAPI），带 currentEnv、userInfoList、
  当前 UID 和目标 UID，目标须能通过 JSK 安全数值范围精确往返。
  当前账号的原生 Cookie 仅发往原有作用域内的切换端点，不复制到
  新候选或前端。其他客户端切换、访客快捷登录、短信不是回退路径。

原生为每次切换使用独立候选。只有真实响应的新 MUSIC_U，且身份与
续期路由均有同一个明确有效的 Cookie，才可通过 account/get 核对。
拒绝把源账号 Cookie 的回显或兼容层补写的 Cookie 当作新凭据。
候选 UID 与目标匹配后，按会话代次、选中记录和目标凭据版本核对，
再更新本机账号选择。迟到响应、错误目标、取消和未支持的额外验证
均不采用候选；保留当前账号。本次请求结果不明时仅允许身份回读，
不重发切换。切换成功后由原生收尾旧账号的播放和下载状态。
切换发包和回包检查期间，会暂缓同一源客户端的其他 HTTP 请求，防止
进程内正常的凭据轮换插入。跨进程修改仍靠版本复核；源版本检查与
最终账号采纳不是同一原子事务，不能声称跨进程锁住源凭据。

证据边界：这是一条由恢复源支持的 PC EAPI 实现，官方 Windows DLL
内部 Cookie 策略和实际服务端凭据轮换仍没有直接证明。测试使用
隔离合成账号，不向真实服务发请求。已核对的账号切换也不等于
跨设备一起听的验证。

合并后的 Linux WebView 与本机 KDE/XWayland（125% 缩放）均通过
8 个状态：资格前后、确认、需其他验证、请求挂起、取消、丢回包后的
身份核对以及采用目标账号。访客快捷登录 7 个阶段也回归通过。
脚本核对取消和回读期间没有重放、访客回退、短信或远端退出请求。
本机截图见 .build/active-switch-desktop-final/contact.jpg。
Linux/Windows CI 分别配置合成探针；本机没有实跑 Windows。
