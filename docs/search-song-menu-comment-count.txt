单曲搜索菜单的评论数
====================

官方 PC 3.1.42.205594 的 SearchResults/components/tab.jsx 和 M352:742–754、
922–945 将单曲分类的目录 Track 交给歌曲行菜单，保留实际行及父表选区。
M556:144–229 在弹出菜单前读取点中歌曲的评论数；songType=1、省略评论
的场景和父级组选区有各自判断。收费或负版权本身不等同于评论不可用。
M3085:4565–4615 先等待菜单项检查，再弹出；「查看评论」仍按原 Track
进入评论页。正数附在文案后，零和读取失败保留普通文案。

独立读取 POST /api/resource/commentInfo/list（M15:1672、M232:824–842），
字段 resourceType=4，resourceIds=JSON.stringify([准确歌曲 ID])。沿用
CommentApi 检查恰好一行、匹配 R_SO_4_<歌曲 ID> 及 JS 安全整数。实服
接口的已有只读记录见 references/recovered-client 的评论功能报告；它
不等于本次单曲搜索菜单已实服验收。此前当前账号的直接单曲搜索与短期
凭据边界见 signed-window-read-proof.txt。

Rust 从当前已认证单曲分类的 baseInfo.simpleSongData 与投影行配对，
只为准确公开目录 ID 签发 songCommentMenu 回执。特殊、本地、声音和
带私有来源标记或身份不明的行不发；普通收费或负版权不单独排除。
回执仅存在内存（最多 16 页、每页 128 行、30 分钟），绑定账号代次、
原生 API 实例与请求凭据版本；与分享、下载、队列和歌单回执各自独立。
主窗口 search_song_row_comment_count 接收 epoch、receipt，用已
绑定的行身份做一次非缓存读，1.5 秒超时退到无数字菜单。仍在原行时，
计数回执驱逐或过期也不会阻止其它菜单项。实际 PC 原生
传输核对账号、搜索和评论数接口的 Cookie 作用域及当前版本，在进入
请求与排队后发出前都校验；迟到或其他账号的结果不得更新菜单。

前端复用原有 ActionMenu 的打开前准备与焦点处理，按来源分别调用歌单
或搜索命令。仅对当前单曲分类、同一结果、原行锚点和单选触发；切换页面
或选区、移动锚点、取消后忽略旧响应。保持评论页面导航、播放、分享、
独立复制的原路由和各自权限。歌词命中另见 search-lyrics-ui-contracts.txt；
综合预览、游客及其它类别保留各自菜单边界。

验收：Linux 上在仅回环网络的 Tauri / WebKitGTK 运行十个状态，分别从
更多按钮、右键及 Shift+F10 调出菜单。核对 6 笔单曲菜单原生读取、另 1 笔
独立播放器评论徽标、准确评论线程、空值/错线程/传输失败、特殊歌曲及多选
不读、离开时 88 不弹出、回到新搜索时显示 51、Escape 焦点回到原锚点、
暂停队列的代次和条目顺序不变。另一次实窗回归核对原有播放、插队及分享
10 态；两次均无真实账号读写。证据在 .build/ui-proof/phase308-search-song-comment-count/
的 search-song-comment-count-r2/report.json、search-next/report.json 及
各目录的 first/ 截图。原生传输集成测试另外解包实际 PC 签名请求，核对大 ID
和 Cookie 作用域；不将它视为对实服的访问。CI 在 Linux、Windows 运行相同
专项，Windows 结果以对应提交的托管运行记录为准。
