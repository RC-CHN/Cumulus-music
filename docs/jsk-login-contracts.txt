选择协议及请求上下文
正式宿主已启用官方登录策略。新候选先读取/复用该账号代次的真实双实验配置，
只有 PH-PC-loginJsk、PH-PC-newLoginBenefit 均为 t1 才选择 Jsk；默认/失败沿用已缓存组或旧链。
实验读取失败不伪造 t1，不在一次密码/验证码提交遭拒后自动改协议重放。
已保存账号切换只读取现有凭据并核对身份，不重新提交密码或为了选择协议增加实验读取。
core/src/account/login/protocol.rs 的 JskLoginApi 只接受固定登录/验证端点，限 PC origin，
明确走 OfficialEapi；fromPage="JSK"、x-login-chain-id="" 在原生层加入。
M/290 getCurrentEnv 没有 loginChainId，空值符合证据，不能伪造一个有效服务链 ID。
请求路径仍经过已有 MConfig/M402 匹配的 RequestContext。没有另造通用易盾或 URS token。
前端无法选择原生协议、注入上述 header、读取 Cookie/refresh token 或二维码完整授权 URL。

主登录接口（以下是业务字段；原生 EAPI 仍添加自己的 header/e_r 和路径匹配令牌）
邮箱：/api/login，username、password=MD5(UTF-8密码)。显式完成滑块后可添加 secureCaptcha。
手机号密码：/api/login/cellphone，phone、password=MD5、countrycode、once、nonce、
secureCaptcha（初次为空字符串）、version="1"。两个随机值为独立小写带连字符 UUIDv4。
CAPTCHA 显式继续重用同一 pending 请求和 once/nonce，不能偷偷重新执行首次登录。
手机号验证码：同 /api/login/cellphone，phone、captcha、countryCode；大小写与密码路线不同。
M/290 verifySms 明确回 success=true、ursToken=""，M/1368 只在非空时传 ursToken，所以原生省略它。
这只是官方 PC 桥的行为，不代表取得或破解了移动端 URS 令牌。
上述新版主登录不带旧链的 remember/type/https 业务字段；remember 仍保存为本机账号自动登录意图，
包括经过滑块继续之后。旧链字段和端点保持兼容。
验证码发送仍使用已恢复的旧 PC UI 原生 /api/sms/captcha/sent {cellphone,ctcode}（另保留 middle helper），
共享真实冷却；M/1368 的 nm.login.sendSms 在 M/290 中缺生产者，没有伪造完整 SDK 发送实现。

二维码：/api/login/qrcode/unikey {type:5}，随后 /api/login/qrcode/client/login
{key,type:5,secureCaptcha:""}；原生 EAPI 的值字符串化与 M/48/M/402 一致。
M/1368 默认 clientType=5，kernelServiceLogin 调用没有覆盖它；新版不添加 lastUniKey。
旧链 type=3/previous-key 行为不变。QrView.pollAfterMs 返回新版1000/旧版2000；Vue串行定时轮询，
上一请求完成才计时，取消/替换后不再接收。801/802/800/803 映射等待/手机确认/过期/授权。
803仍要读 /api/w/nuser/account/get 核对身份、候选代次和当前账号，才能提交保存；取消后的迟到803
不能发布账号或保存为当前账号。二维码 key 仅用于原生生成模块矩阵。

二次验证及票据寿命
每个原生 JskLoginApi 有自己的 JskLoginContext，不能跨候选、账号或普通业务复用。
只在实际验证事件对应的8830/8860/8831响应中从原始 Set-Cookie 提取 MUSIC_TU；
不从业务正文或持久 CookieJar 猜测。即使该 Cookie 的 Path 不匹配后续端点，事件票据仍可作为
x-music-tu 发送；反过来，验证码8821或 begin/list/send 的普通回执不能替换这个事件状态。
该头只在候选的已列举 JSK 登录/验证请求中传递；普通身份读取和新候选没有旧头。
M/1368 getVerifyList 先 /api/user/2fa/begin {}，再 /api/user/2fa/list
{bindingCellphoneEnable:true,smsCaptchaAble:true}。begin 的网络/服务失败按 SDK 行为仍继续读列表，
不重发 begin；取消/失效仍立即停止。旧链保留原有 list→begin 顺序。
现有两步验证投影/动作白名单继续适用；安全邮箱发送/核验、短信核验、安全问题和换绑确认
使用 desktop-login-contracts.txt 的精确端点。这里仅接通已支持动作的 JSK 上下文，未声称完成
SDK所有验证方法、处罚8831的steps/musicTuP处理、实名认证或微信授权。
未知方法继续明确显示边界，不自动发信、提交答案或绕过服务端挑战。
UI显示未接入的绑定手机号选项时，不再暗示当前账号必须绑定；已支持的安全邮箱仍可继续。

令牌接收与自动续期
core/src/protocol/http/login.rs 明确列举成功登录路径。完整 HTTP 2xx、业务200（QR803亦可）
才能采纳 x-refresh-token；新主登录端点现已加入旧登录/QR/刷新白名单。
已恢复的验证完成端点必须同时实际返回非空 MUSIC_U Cookie，才有资格保存其 refresh header；
单独200确认、begin/list/send/get 回执、部分正文、错误HTTP/业务码、非JSON均不能安装刷新令牌。
普通 Cookie 的记录继续支持未知结果后的显式身份核对；不会自动重放原密码/验证码。
账号候选通过身份核对后才成为活跃账号，秘密存于该原生账号库，公开 DTO 不包含它们。
续期触发、24小时间隔、签名、成对轮换和未决持久恢复见 desktop-session-renewal-contracts.txt。
获取和轮换是两个条件：接收逻辑已具备，不等于服务器保证下发，更不等于真实账号轮换已通过。
