Explicit existing PC state: signed full-batch search read proof
===========================================================

core/examples/search_signed_read.rs is an opt-in research/native read runner.
No arguments performs no account/profile/network access. An explicit invocation
requires the existing desktop state root and a new private output directory:

  search_signed_read --existing-pc-state EXISTING_STATE NEW_PRIVATE_OUTPUT

An explicit --fresh-local-identity flag permits a second mode: real local
hardware facts initialize a new, empty identity store under NEW_PRIVATE_OUTPUT.
It uses the production IdentityService::resolve and Windows compatibility
profile construction. It never imports a historical installation identity or
changes either original credentials or the copied primary record. Reports label
this fresh_local_initialization, not restored_installation. This flag does not
relax native PC configuration, signature, Cookie scope or HTTP/SDK restrictions.

An independent --include-account-resources flag enables the production account
playlist and liked IDs reads before search. The saved registry must bind exactly
one verified UID to the selected session; the signed account response must
match it before any resource or search dispatch. This does not send the UID to
the report. Both flags can be used together.

The original state is opened read-only. SQLite's native backup API snapshots
the registry/context database and selected credential database, including any
committed WAL content; it never copies live database files directly. Persistent
identity and real local hardware feed the same recovered clientSign/profile
construction as desktop Linux Windows compatibility. An existing native PC
configuration with nonzero version/data is mandatory. Neither a default UA nor
a fabricated configuration/signature can satisfy that requirement.

Only these PC EAPI reads may leave the process:
  /api/w/nuser/account/get
  /api/user/playlist (only with --include-account-resources; selected UID,
    includeVideo=true, limit=200, exact next offset, at most 16 pages)
  /api/song/like/get (only with --include-account-resources; selected UID once)
  /api/rtrs/abt/front/expinfo/list (the complete checked-in 190-key vector)
  /api/search/pc/result/tab
  /api/search/pc/complex/page or /api/search/pc/complex/page/v3
The three search paths require one fixed public keyword. Account verification
precedes the native full-batch consumer; search then consumes that same shared
assignment through the production search assignment/footer gate. No short-bucket
fallback, playback source, login, refresh, SDK/challenge, payment or write route
is allowed. Redirects and transport retries remain disabled.

Saved native path policy is respected: a path requiring a fresh SDK token stops
before dispatch. TokenProvider never obtains or fabricates a token. Configuration
downloads also stop locally; a failed ancillary config update does not replay a
music request. The report records these demands as explicit boundaries. A stale
or rejected session is not repaired by QR, renewal, expanded Cookie scope or a
different protocol.

Only aggregate result counts (including playlist/owned/liked counts when
requested), four t1 booleans (searchHot, searchMore2,
searchPageEfficiency, search-result), fixed logical read paths and HTTP/service
codes enter the report. It excludes account IDs/names, Cookie, tokens, clientSign,
hardware facts, full authorization URLs and raw replies. The isolated state is
private evidence under .build and must not be committed. Errors are classified;
raw error Display strings are never printed.

Synthetic runner tests cover the full-vector/fixed-search allowlist, a live
committed-WAL backup, fresh-identity isolation from an existing primary,
unique local account binding, and blocked cross-account/duplicate/early reads
and incorrect pagination.
They do not establish a live service result. The
global M147 startup/30-minute reactive experiment lifecycle and cached Vue footer
updates remain a separate required implementation; this explicit read runner
does not claim to complete it. Current source and execution evidence are recorded
separately after the exact new example is built; older generic search CLI results
do not validate this signed path.
