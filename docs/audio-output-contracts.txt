接口与内存边界
- AudioEngine::output_devices -> Option<OutputDevices>；None 为引擎不支持，
  也用于明确配置 null 输出的验证引擎。普通 MpvEngine 返回真实枚举结果。
- devices[].id 是原生不透明字符串，description 为显示文本。保留大小写，
  不把 Windows WASAPI ID 换算成 Linux ID，不解析或拼造驱动参数。
- configured 是请求配置；active_driver 是当前后端，未初始化音频时为空。
  二者都不是实际物理设备身份证明。测试已复现设备拔除后 configured 保留旧值。
- set_output_device 在每次变更前重新枚举，只接纳本次列表里的完整 ID；
  拒绝空值、NUL、超过4096字节、列表外或已拔出的设备。不修改 ao、播放状态、
  当前文件或播放位置。成功返回仅表示配置命令得到确认，随后仍可能初始化失败。
- null_output 引擎不枚举硬件并拒绝所有选择，包含 auto；不能借设置接口脱离
  静音测试隔离。音频焦点包装和 MpvVideoEngine 转发相同能力，但不会获得播放权。
- mpv_get_property_async(audio-device-list, MPV_FORMAT_NODE) 独立序号匹配，
  5 秒等待上限；迟到回复不满足新请求。读取时保留播放事件供原播放器消费。
  配置命令复用原有异步5秒等待；设备可能在枚举后消失，调用方仍须处理失败。
- 唯一不安全内存读取位于 engine/ffi/devices.rs；按标记检查 ARRAY/MAP/STRING，
  复制事件内的设备字符串后才允许下一次 wait。事件节点由 mpv 管理，不能由
  Rust 调用 mpv_free_node_contents。最多1024设备、每设备64字段、字符串16KiB；
  重复ID/必填字段缺失/错误格式/错误UTF-8均失败，未知附加字段不解引用其 union。
  这些约束检查可信 native ABI 的数据形状，不能防护恶意原生库提供的任意指针。
- 原生调用只在阻塞工作线程执行。现有同步属性字符串读取没有新增硬取消保证；
  不把异步枚举的5秒上限描述为整个 libmpv/系统驱动不可卡住的保证。

   未加载音频的枚举器检查 auto 与无活动后端，并拒绝非法选择；显式 null 引擎
   拒绝选择，之后照常完成PCM解码、播放/暂停/定位、CUE EOF/复位/取消。
   两平台既有CI会执行这些探针；不能用Linux通过替代精确提交Windows结果。
3. Linux两虚拟设备完整路由测试：
   cargo build -p cumulus-desktop --example native_audio_probe --features custom-protocol --locked
   LC_ALL=en_US.UTF-8 GDK_BACKEND=x11 WEBKIT_DISABLE_DMABUF_RENDERER=1 LIBGL_ALWAYS_SOFTWARE=1 \
     dbus-run-session -- xvfb-run -a python3 scripts/ci/output_devices_smoke.py \

   依赖 PipeWire/pipewire-pulse/pactl/WirePlumber 的 policy-only profile。
   使用临时 runtime socket、隔离的 XDG 目录和仅策略会话管理器，不启用硬件监视器；
   建立两个 null sink。测试探针只允许加载到指定的隔离 Pulse 设备，生成60秒静音PCM。
   由独立 pactl 查询实际 sink-input 路由，不用播放器 configured 字段自证切换。
   检查 a→b→a→b→a、播放中切换、暂停切换及实际cork/静止时钟、旧ID拒绝、

2026-10-29 Windows 原生枚举销毁故障与 COM 生命周期
- 精确提交5cac320的CI 40775618163诊断：MSYS2 UCRT64 mpv 0.41.0-10、
  ffmpeg 9.0.2-2、libplacebo 7.387.0-1。Rust完成枚举、auto选择和再次枚举后，
  在枚举器销毁前退出0xc0000005；独立ctypes直接C ABI复现同样销毁故障。
  single-sync/pair-sync全部查询、选择、销毁和DLL卸载通过；single-async、
  pair-async、pair-async-drain均在mpv_terminate_destroy访问异常。C对照没有
  Rust节点解析，提前排空事件仍失败；upstream mpv --audio-device=help通过。
- 8d3449d / CI 40777119985尝试公开异步expand-text命令读取同一属性JSON：
  Linux六项边界测试、1079项全量Rust、GUI原生解码及两虚拟设备实际路由均通过，
  但Windows单/双实例C命令同样在销毁时失败。因此“仅异步属性回复有问题”的
  初步范围不成立，JSON命令并未修复；最终恢复原有异步NODE枚举及边界测试。
  device-command-*证据属于该中间提交，不把它当最终Windows成功记录。
- 源码给出新的生命周期假设：mpv v0.41.0的WASAPI hotplug_init在调用线程
  CoInitializeEx(MTA)并保留IMMDeviceEnumerator；异步属性在core线程求值，
  client.c:486–489却先join core线程，再由销毁调用线程运行mp_destroy。
  因而COM资源有可能先于仍待清理的枚举器结束。尚未取得崩溃栈，不声称已经
  定位具体访问异常指令；用下面的独立C对照验证此假设。
  https://raw.githubusercontent.com/mpv-player/mpv/v0.41.0/audio/out/ao_wasapi.c
  https://raw.githubusercontent.com/mpv-player/mpv/v0.41.0/audio/out/ao_wasapi_changenotify.c
  https://raw.githubusercontent.com/mpv-player/mpv/v0.41.0/player/client.c
- Windows Native持有CoIncrementMTAUsage返回的独占cookie，先于mpv_create
  获取；mpv_terminate_destroy及render线程结束后，仅调用一次CoDecrementMTAUsage，
  最后卸载libmpv。构造失败也由RAII释放；不泄漏进程全局COM引用，不替换已有GUI
  STA，不创建未受控线程，也不改同步/异步枚举、超时、设备完整性或播放业务。
  Microsoft明确允许该cookie跨线程释放；这不是要求同线程释放的CoInitializeEx。
  https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-coincrementmtausage
  https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-codecrementmtausage
- scripts/ci/windows_device_diagnostic.py默认验证Rust生产探针、单/双实例同步
  对照，以及持有/释放MTA lease的单/双实例异步属性和异步命令；全部必须成功。
  --unguarded-async-probes额外运行没有lease的原始故障对照，任何失败仍返回非零；
  不以continue-on-error或忽略生产路径失败通过CI。真实WASAPI设备路由仍须实机。
