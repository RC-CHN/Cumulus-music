PC 3.1.42.205594｜播放队列「更多推荐」的歌单来源

官方证据
  M/1384:5275–5302、6451–6530：只有清空替换队列才更新资格。全局
  PH-PC-recommendMore=t1 后，originalResourceType=playlist 单独读取
  PH-PC-recommendMore-songList。t4 在 ID 和归属判断前放行；其他组
  要求 sourceData.id。先查星标歌单 ID（t3 特例），再排除自建，
  再限制收藏歌单为 t2/t3。剩下的其他歌单也允许缺省组。
  M/3160（hybrid_105）:923–973 从当前 UID 的完整列表建
  createPlaylist / favPlaylistIdsMap，并取 specialType=5 的星标 ID。
  M/232:213–269、M/15:1316–1328：/api/user/playlist 的记录按所有者
  分组；官方还合并置顶读。M/15:1409–1415 是 v6 详情；M/444:133–173
  说明 playlist.subscribed 是当前查看者是否收藏，而 subscribedCount
  是人数。官方 v4 路径可从 dynamic 详情补这个布尔值。
  PlaylistMetaCard/index.jsx:222–240 和 playlist/views/TrackList.jsx:234–241
  提供对应歌单来源。保留队列的行操作、追加、下一首不是清空触发。

Rust 规则与边界
  只有普通 PlaySelection::Playlist 确实替换队列时，才使用原本就要
  读的 /api/v6/playlist/detail 判定；回包的规范数字 ID 必须与请求 ID
  匹配。判定随本次原生队列替换保存，渲染层只看到是否可用，不收到
  归属、实验回包或授权材料。现有按账号保存的队列继续隔离不同 UID，
  运行时实验回包也要匹配当前代次；旧队列没有证据时不会补推来源。
  详情里的所有者、specialType 与当前查看者 subscribed 布尔值优先；
  缺字段时只使用已经成功读取的侧栏记录和现有星标提示的正向证据，
  两者均要求同一 SessionToken（含 UID 与代次）。侧栏缺行、收藏数、
  外部页面标记及前端声明都不证明归属。相互冲突的所有者不用于归属。
  无法分类的匹配 ID 只在明确 t4 时可用；即使 t4，缺失/不匹配的详情
  ID 也不创建来源。没有新增归属、置顶、dynamic、曝光或实验请求；
  只复用现有签名分组及既有的推荐 → 权益读取。
  此批不扩大批量选曲、保留队列的双击、追加、专有来源或一起听。
  来源在下一次清空替换时重新判定，不因打开队列重复查询歌单。没有
  真实服务请求；合成原生测试覆盖 4 组 × 7 类、现有请求计数、推荐和
  权益两段回包、同 UID 重登与不同 UID 隔离，不代表平台实服分组结果。
