关键纠正
云信聊天室登录、入房、收到 msg_type=5 入房通知，只证明聊天室传输可用。
官方 im.onChatRoomMsg 这一前端事件名称不能反推它来自 nim_chatroom 的消息回调。
本次沿 nim_wrapper.dll -> cloudmusic.dll -> M/75 完整追踪，确认一起听业务入口来自
nim_talk_reg_receive_cb 和 nim_talk_reg_receive_msgs_cb，取 IMMessage.attach_（msg_attach）。
不是 msg_body，不是聊天室通知的 msg_attach，也不是任意 JSON 递归搜索出的 type。
旧报告的“未收到播放业务包”结论保留；不能据此断言服务端不会向单账号推送业务消息。

官方二进制证据
所有地址均为本次恢复版本的静态地址。详细地址、二进制哈希与字段关系见
references/yunxin-sdk-research/native/business-message-evidence.json。
nim_wrapper.dll 注册点 RVA 0x3902/0x39ce，分别将 0x63b0/0x6340 绑定到普通/批量接收；
0x19b40/0x19d60 动态加载对应 nim_talk API。
IMMessage 解析器 0x1b870：msg_body 写入 +0x58，msg_attach 写入 +0x80。
单条接收 0x63b0 读取 +0x80；批量接收 0x6340 读取链表节点 +0x90（节点数据偏移+0x10），
都调用接收者 vtable+0x60。
cloudmusic.dll 的该槽为 0x1812ac570，复制字符串并投递到 0x1812aa140；
后者调用监听者 vtable+0x08，对应 0x180f5a060，形成 im.onChatRoomMsg 的 msg 字符串。
前端 M/75 原文 JSON.parse(e.msg).content，再按 type/content 分派。
原生桥里的 roomid 来自控制器当前房间，不能代替消息本身的房间归属证明。
这些证据只读反汇编取得；没有执行官方 Windows 包，也没有使用 YesPlayMusic。

Rust 实现
core/src/listen_together/native_im/ffi.rs 新增准确的三参数 TalkCb ABI 和两个接收注册口。
callbacks.rs 在原有不可复用 cookie/Weak 注册表、安全复制、限长、非阻塞队列边界内接收。
只保留已恢复的一起听附件：普通聊天正文、发送者元数据、未知类型均不会进入业务事件。
原始输入和批量输入按 SDK 官方 ParseReceiveMessage 兼容；有 content 外层时须 rescode=200。
无外层的原始消息对象也支持；不将正常聊天 msg_body 作为业务附件后备入口。
解析错误/未知附件不触发播放或房间写入；输入仍受单次1MiB及serde递归限制。
ImEvent::Business 与 RoomMessage 均无 Serialize，Debug 隐去身份及内容。

message.rs 精确解码以下 type：
20000 PLAY_COMMAND，20001 PLAYLIST，20002 USER_JOIN_IN，20003 END_LISTEN_TOGETHER，
20004 VIP_GIVE，20005 DIGITAL_GIVE，20006 VIP_STATUS_CHANGE，20008 HEARTBEAT，
20009 DISTANCE_CHANGE，20010 STATISTICS_CHANGE，20011 DIGITAL_STATUS_CHANGE，
20012 PRIVILEGE_STATUS_CHANGE，20013 EMOTICON_SEND。20007没有恢复定义，不擅自填充。
transport/worker.rs 仅将 content.roomId 与当前音乐房间相等的消息传给房间 Runtime。
不同房间、缺少房间ID、旧账号代次被隔离；接收计数只增加实际通过过滤的业务条目。
运行上下文再次校验房间，并按 M/75 重置20秒空闲心跳。
目前缺 roomId 的业务消息会被正式宿主丢弃；需继续恢复其他可证实的归属方式或取得真实样本，
不能为了“支持”而把控制器当前房间直接套到排队的旧消息上。
