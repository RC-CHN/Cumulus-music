Windows 真实本机硬件 collector：下一批实施方案与证据边界
2026-11-04；状态：静态恢复与验证方案，尚未实现或进行 Windows 设备实采。

本文件不改变当前默认配置。当前 Windows 默认/windows-local 只声明官方兼容 UA/osver，
不调用 Linux collector、不补造 clientSign。后续工作要增加的是 Windows 本机事实来源，
不能把本方案、Windows 编译成功、Linux 合成测试或现有声明映射称为 Windows 采集完成。
原方案还核对了锁定的 Windows crate 和 Microsoft API 文档；本次新增证据来自同版本
解包 DLL 的只读反汇编、导入表及常量，没有执行官方 DLL、发请求或读取真实设备字段。

1. 已有官方字段和字节证据

主要依据为 cloudmusic.dll x64 3.1.42.205594，SHA256：
557d7706dedc8556a8bd279d4dfe2bc05b80ad729a8749caccd9e29916935493。
以下为静态恢复证据，不表示已执行官方 DLL 或取得同机 Windows 指纹对照。

- CEDF80：按 mask 低四位处理 MAC、磁盘、主板/BIOS 序列、持久 ID；正常宿主 mask=15。
  后续启用项在已有累计输出非空时先加 @，空项仍可保留分隔符。
  来源：protocol/core-more/regions/00cedf80.asm；已有 Rust composition.rs 已承接该规则。
- CF2A00：直接连接 MAC 与磁盘，不插入额外分隔符。
  CF42E0：调用 WideCharToMultiByte(codePage=0, flags=0)，即 CP_ACP；摘要不含末尾 NUL。
  CF1940/CF1C80：first=lower_hex(MD5(hardwareBytes||hostBytes))，
  persistentID=first||lower_hex(MD5(ASCII(first)))。主板序列不参与这个摘要。
- MAC，CEF5E0（core-more/regions/00cef5e0.asm:30–32、80–108、171–173、
  218–248）：先取 CF0130 的结果，完全等于 `FF:FF:FF:FF:FF:FF` 或包含
  `00:00:00:00:00:` 则清空；只在此结果为空时转 CEFD10，并再次执行相同过滤。
  后一个匹配是子串检查，不等于仅拒绝六个零字节。
  CF0130（cache-encoding/regions/00cf0130.asm:39–94、117–128、146–229、
  257–260、308–311）按 RegEnumKeyExW 的原次序扫描 HKLM 的
  `SOFTWARE\Microsoft\Windows NT\CurrentVersion\NetworkCards\`；将 Description
  转小写后过滤包含 `virtual` 或 `1394` 的条目，再读取 ServiceName。首个非空
  CEFA40 结果交给外层过滤；外层拒绝后转备用分支，不继续扫注册表下一条。
  CEFA40（x64 DLL RVA CEFA40–CEFD08，尤其 CEFB42–CEFC9E）在名称前拼
  `\\.\`，CreateFileW 使用 GENERIC_READ、FILE_SHARE_READ、OPEN_EXISTING；
  DeviceIoControl 使用 0x170002，输入四字节 0x01010101（OID_802_3_PERMANENT_ADDRESS），
  成功时格式化返回的前六字节。格式是六组大写 `%02X`，以冒号分隔。
  CEFD10（cache-encoding/regions/00cefd10.asm:19–33、43–81、99–124、163–194）
  用 gethostbyname(gethostname()) 的首个 IPv4；在 GetAdaptersInfo 的链表中匹配
  `Type == 6` 和首个 IpAddressList 地址（偏移 +0x1a4 是 Type，非 AddressLength）。
  先用 AdapterName 再试 CEFA40，空才格式化记录的前六个 Address 字节。
  这些路径没有确认现代驱动是否允许查询、DNS/多 IPv4 选择或网卡随机化的实测覆盖。
- 磁盘，CEF440（core-more/regions/00cef440.asm:32–43）：CF4930 取窄序列，
  经 CEE4D0 转为宽串，CF1120 修整外侧 CRT 空白，再用与主板相同的 CEE8E0 校验。
  CF4930（device-fingerprint/regions/00cf4930.asm:16–44）对 NT 平台依次尝试
  CF5BA0（SMART）、CF5650（SCSI miniport）、CF5E50、CF5900，按成功状态短路，
  不能直接挑较易实现的分支代替此顺序。
  CF5E50（同目录 00cf5e50.asm:30–95、103–226、263–387、444–445、512–521）
  从 PhysicalDrive0 起枚举到 15；CreateFileW 访问权 0、share=3、OPEN_EXISTING，
  传 12 字节零初始化查询结构（StorageDeviceProperty / PropertyStandardQuery），
  DeviceIoControl(0x2d1400) 输出 0x2710 字节，descriptor +0x18 取序列偏移。
  解码每四个十六进制字符时先取后两字符的字节，再取前两字符的字节，非零才追加。
  此后按 CRT 窄字符字母数字（掩码 0x107）、空格、连字符等检查；有返回原始文本
  或再清理文本的路径。另有 DeviceIoControl(0x2d0c10，即
  IOCTL_STORAGE_GET_MEDIA_SERIAL_NUMBER) 回退；它不是 GetVolumeInformationW。
  尚未冻结各返回分支的空值、非法或奇数长度、非 ASCII、控制器以及 SMART/SCSI
  优先级向量；即使取到真实存储描述符，也不能宣称整个磁盘采集对齐。
- 主板，CEEFF0（core-more/regions/00ceeff0.asm:19–20、46–64、81–98、
  115–119、156–162）：在同一 WMI 对象上先查主板、再查 BIOS，两次查询都在
  选择前发生。优先返回校验通过的主板；清理后为空才采用校验后的 BIOS。
  CF7D80（x64 DLL 直接反汇编）初始化 MTA COM，连接本机 ROOT\CIMV2，
  调用 CoInitializeSecurity、CoCreateInstance、CoSetProxyBlanket。
  D00510 与 CFDC10（device-fingerprint/regions/00d00510.asm:23–51、
  00cfdc10.asm:23–49）分别构造 `SELECT * FROM Win32_BaseBoard `、
  `SELECT * FROM Win32_BIOS `（末尾各有一个 U+0020）并取 SerialNumber。
  CFE940（同目录 00cfe940.asm:65–73、110–143）以 WQL、0x30（半同步、只向前）
  调用 IWbemServices::ExecQuery，再 IEnumWbemClassObject::Next(-1, 1)，只处理
  首对象；调用 IWbemClassObject::Get，并非遍历寻找首个可用序列。
  D02970（x64 DLL RVA D02970–D02AAE）用 WideCharToMultiByte(CP_ACP, 0)；
  CF7680（同目录 00cf7680.asm:29–57）用 MultiByteToWideChar(CP_THREAD_ACP, 0)。
  第二次转换传 `cbMultiByte=-1`、`cchWideChar=探测长度-1`，不检查该返回值，
  之后自行终止字符串；磁盘和网卡名称用的 CEE4D0 也有同形调用。
  必须在真实 Windows 核对此目的缓冲区边界的实际输出，不能用无损 BSTR 直读
  假定等价。D02660/D026A2 删掉每一个 U+0020；并非去除所有 Unicode 空白。
- 共同校验 CEE8E0（x64 DLL RVA CEE8E0–CEECC6）：长度至少 80 时保留首 79 个
  UTF-16 代码单元（CEE94C–CEEA4C）；少于 6 个或每个单元均匹配 CRT digit 类时
  清空（CEEA73–CEEABF，经 C99378/CCA044 掩码 0x4，非单纯 ASCII 正则）。
  对工作副本按 CRT locale 转小写（136EE4C/136EBCC，LCMAP_LOWERCASE 0x100，
  C locale 走 ASCII 小写）；按字面子串依次检查 `unknow`、`oem`、`o.e.m`、
  `invalid`、`diy`（CEEB8A–CEEC68；只读常量 VA 0x181B9EBB0–0x181B9EBEF）。
  命中清空原值，未命中保留原大小写。不得添加其它 OEM 词并称为官方判断。
- CF9C10(type=0) -> D01400：主机说明来源是 Win32_ComputerSystemProduct 的 Vendor/Name，
  并非机器 hostname。机型判断另取 Win32_SystemEnclosure.ChassisTypes。
  WMI 失败时 CFD2D0 读取 HKLM\HARDWARE\DESCRIPTION\System\BIOS 下的
  SystemManufacturer/SystemProductName，D01F40 另有 SetupAPI 机型路径。
  “主机:”和两种机型描述在 DLL 内是 GBK 窄字节常量；失败可能得到整个空说明。
  WMI 文本到窄字节的完整转换、SAFEARRAY/机型异常分支仍须恢复并以 Windows 对照确认。
- 副设备文件的硬件绑定字节另走 CF1510(codePage=3，即 CP_THREAD_ACP)，
  不能把它与上述 CP_ACP 摘要路径合并。本方案不实现副文件绑定或自动修复。

2. Linux 适配策略不能当作 Windows 证据

core/src/identity/facts.rs 当前只提供 collect_linux_identity(/sys)：
MAC 优先物理、其次 up、最后接口名；磁盘按受限设备名排序选可读序列；主板缺失时取
product_serial；占位词过滤、Unicode 空白清理、整段 GBK 编码及 chassis 类型集合都是该适配器
的具体策略。不能把这些排序、fallback 和编码无条件用于 Windows，再称之为官方 WMI/SCSI。
特别不能将 Windows 上不存在的 /sys、磁盘型号、卷序列号、MachineGuid、用户名或随机值
充当 MAC、物理磁盘序列、主板序列。

3. 建议的最小实现范围

建议把 Win32/COM 适配留在 desktop 的原生平台层，例如 desktop/src/identity/windows/，
只向独立 core 交付 HardwareFacts::from_encoded 接受的真实字段和已确认窄字节。
core 保留组合、摘要、校验和 IdentityService 事务，不引入 Tauri、WebView 或脚本子进程。
现有 Linux collector 的位置不要求为此批顺便重构。
若未来 core CLI 也需要独立 Windows 自动采集，应另安排低依赖共享适配层或 core 的 Windows
目标依赖；desktop 已依赖 Windows crate 并不等于 core 已有可直接使用的同名依赖。

首批只做隔离的离线 Windows 探针。主板最适合先实现：按固定 WMI 路径、
查询顺序、首对象和清理规则取值，处理已确认的 BSTR；错误类型、越界和无效结果
留空。对原生代码可能直接读错误 VARIANT 指针、无限等待和进程级 COM 安全初始化，
使用受限失败语义并记录差异，不能将替代行为描述为逐分支完全一致。

MAC 的两条路径可以按上述接口和顺序准备，但只有 Windows 验证能确认设备名、
驱动权限、是否需要解析器通信，以及永久地址与当前地址的实际结果。离线探针的无外网模式
若不能完成原 fallback，就记录不可测；不换成第一块网卡或 GetAdaptersAddresses。
磁盘只将 CF5E50 的零访问权路径作为独立实验，不接到签名；对 descriptor 长度、
偏移、终止和 IOCTL 响应校验失败时留空。SMART/ATA/SCSI 的不同权限及设备兼容路径
需另审，不为模拟提权、不在生产发送未确认安全的 IOCTL。主机描述也继续独立验证，
避免用 hostname、型号、卷序列或任意代码页假装恢复。

本阶段不修改 Windows 默认、windows-local 或账号请求。未经下面的 Windows 对照，
不得将部分采集结果接入生产请求、持久 ID 创建或替换。所有字段缺失时仍明确报告
不可用，不能发示例序列。即使探针通过，开启默认或写入持久状态也应另成批次。

4. 字节、已有 ID 与首次派生必须分别处理

HardwareFacts/DeviceIdentity 不实现 Debug 或 Serialize；源信息只记录适配器版本、可用性和
必要的非秘密接口/设备索引。完整 MAC/序列/派生 ID 不进 IPC、界面、常规日志或公开 CI artifact。
原生 bytes 与用于 clientSign 的规范化文本应分别持有，不能对窄字节先 lossy 转成 UTF-8 再摘要。
Windows 的 CP_ACP 不能硬编码为936；也不能为了让结果“像官方”修改进程/系统 locale。
代码页替代字符、无法表示的文字及 UTF-8 ACP 场景要有明确处理规则和合成对照，
严格拒绝有损转换如不同于原生 flags=0 的行为，必须明确记录差异。

已有合法 persistent_id：继续由 IdentityService 在同一 BEGIN IMMEDIATE 事务中优先使用；
硬件、代码页、选择策略或 collector 升级只更新观察字段，不能自动重新派生第四段。
已有 ID 无效、数据库损坏、事务/持久化失败仍应报错，不得伪装成“无硬件”而轮换或降级。
账号凭据 deviceId 始终归 Credentials 管理，不由本机硬件 ID 覆盖；不自动读取或写入官方
COMMON_APPDATA、安装目录、isc.dat/isc_chat.dat，也不改变 Cookie 作用域。

首次创建：现有 HardwareFacts::from_encoded 只要求前三段至少一项非空；但摘要不含 board。
因此“仅 board 非空，MAC/磁盘皆空，且 host_bytes 也为空”会使 hardware_bytes||host_bytes
为空，跨机器得到同一个确定性 ID。这个碰撞前提不能省略为“任何 board-only 都必然同 ID”：
host_bytes 非空时摘要输入不再为空，但同型号主机说明本身仍不保证单机唯一。
建议新增仅供原生构造使用的首次派生质量策略，至少拒绝空摘要输入；更保守的 Windows 默认
可要求首次创建具有真实 MAC 或磁盘输入。后者是新增策略，不是已证实的官方额外判定。
该检查必须放在事务内“确实不存在既有 ID”的分支，避免先查后写竞态；不能把同样条件用于
否定一个已经合法持久化的 ID。可保留原 resolve 接口行为，另用类型化构造选项约束新适配器。

若先用缺主机说明/缺盘序列的子集创建 ID，后续补齐字段也必须保留这个首次 ID。
所以追求同机官方 ID 逐字节对照时，应先完成序列/主机字节规则，或在单独离线探针中研究；
不要为了赶默认开启而先写不完整 ID，再在以后自动旋转“修正”。

5. COM、超时与持久化边界

使用一个原生工作线程采集；线程自行 CoInitializeEx(COINIT_MULTITHREADED)，在同一线程
释放所有 COM 接口/BSTR/VARIANT/SAFEARRAY 后再 CoUninitialize，不改 GUI 线程已有 STA。
现有 core 播放器 Mta 使用租约只维持 MTA 生命周期，不是该工作线程的 CoInitializeEx guard。
不在库内随意调用进程范围 CoInitializeSecurity；需要的身份/认证设置限定在本地 WMI proxy，
例如 CoSetProxyBlanket，不为采集修改整个应用的 COM 安全默认值。
只使用固定 ROOT\CIMV2 与固定 SELECT 查询；不暴露任意 namespace、机器名、账号或查询字符串。

WMI 使用半同步、仅向前枚举，Next 采用有限毫秒数、有限对象数和总 deadline。
须同时检查 HRESULT 与返回对象数：WBEM_S_FALSE 仍可能带最后一批对象，不能直接丢弃。
字符串和 ChassisTypes 的实际 VARIANT/SAFEARRAY 类型、维度、上下界均要检查，
不能把 union 指针当字符串，或只照某个反汇编偏移强转。

ConnectServer 默认可能无限等待；WBEM_FLAG_CONNECT_USE_MAX_WAIT 也只保证不超过两分钟，
不是一个适合 GUI 启动的短超时。调用方应另有明确的短 deadline、一次启动最多一次采集，
超时只接收声明配置或返回严格模式错误，不连续新建重试线程。
工作线程只产生内存中的事实，不持有 StateStore。只有主线程在当前启动仍有效、结果按时被接纳
之后才调用 IdentityService。这防止迟到的采集结果暗中创建 ID、更新观察或触发账号初始化。
丢弃线程句柄/接收超时不等于取消底层 WMI 调用，不能将其宣称为已经硬终止。
若必须保证内核/COM 卡死也被强制终止，应另设计同程序的受限原生 helper 进程和 JobObject，
不借用 Python/PowerShell；这不是当前最小线程方案已经具备的能力。

Win32 IOCTL 如使用 overlapped I/O，CancelIoEx 只提出取消请求，不保证操作已完成。
OVERLAPPED、缓冲区和句柄必须活到实际完成，不能在调用方超时后释放仍被驱动使用的内存。
RAII 应分别处理 HANDLE、HKEY、COM/VARIANT 的真实释放函数和失败哨兵，不使用一个通用
CloseHandle 包装所有资源。缓冲区对齐、长度/整数转换、链表指针范围/循环和枚举数量都需有界。

6. 可复用依赖和下一批接线

desktop/Cargo.toml 已固定 windows=0.61.3，另有 windows-sys=0.61；Cargo.lock 已有对应版本。
可复用 windows 的类型化 COM/Win32 包装，新增目标专属 features：
Win32_NetworkManagement_IpHelper、Win32_Storage_FileSystem、Win32_System_IO、
Win32_System_Ioctl、Win32_System_Com、Win32_System_Ole、Win32_System_Variant、
Win32_System_Wmi；采用已确认注册表分支时再加 Win32_System_Registry。
Win32_Foundation、Win32_Globalization 已在该 windows 依赖启用。
若使用 GetAdaptersAddresses，还需该绑定要求的 Win32_NetworkManagement_Ndis 与
Win32_Networking_WinSock。不能把 windows-sys 的某个 feature 当成已为 windows 同时启用。
本方案不需要新增 WMI 脚本依赖或执行系统命令。

后续接线仍从 desktop/src/identity.rs 原生启动配置进入：
先采集/接纳实际事实，再由 core 事务解析持久 ID，最后构造 ClientProfile，之后才初始化账号。
计划启用后的默认/windows-local 可使用 Windows 声明加真实 Windows facts，native 继续恢复旧
平台默认；local 在 Windows 的新语义、缺硬件/超时的默认回落与显式严格错误需要另写契约。
任何回落都只能包住已分类的采集不可用，不得捕获 StateStore/既有 ID/持久化错误。
这些行为目前未修改，仍以 docs/default-windows-compatibility.txt 的现有边界为准。

Windows 离线对照顺序：

1. 冻结合成向量，分别断言首对象、双查询顺序、删除 U+0020、长度 5/6/79/80、
   数字分类、混合大小写占位词、未命中时保留原样、无效主板改取 BIOS。
   最小例 `AB 12 CD` 在完成代码页转换后应为 `AB12CD`；`12 3456`、`VendorOEM-01`
   应清空；第 80 个位置开始的占位词不能影响前 79 个单元。Unicode 码点边界需用
   UTF-16 测，不以 Rust 字符数或 Unicode 大小写规则冒充。
2. 在 Windows runner 的隔离进程中验证 WMI 首对象和受限缺失行为，不使用账号；分开测试
   CP_ACP 与 CP_THREAD_ACP、短目的缓冲区的返回值及是否写入、当前 UTF-8 ACP 与传统
   ACP 的情形。不能把标准转换推断成这条已恢复链路的输出。需要真实 Windows 观察值；
   Linux 合成向量只证明解析器，不证明 Win32 调用行为。
3. 在同一 Windows 环境比较永久/当前 MAC、注册表顺序与 IPv4 选择；至少覆盖虚拟、
   1394、无效地址、多个 IPv4、NDIS 拒绝及 fallback，无 DNS 条件不可用就明确记录。
   冻结磁盘 SMART/ATA/SCSI/存储描述符、不同端序与非十六进制、截断/无 NUL/越界、
   同一设备多分支以及 0–15（含）扫描的合成响应；真实普通用户驱动探针单独记录成功和拒绝。
4. 若可在授权的独立 Windows 环境对比官方解包版，只比较同一时刻的字段一致性、分支和
   长度区间，不保留真实 MAC、序列、主机名或完整 clientSign。官方材料或真实硬件比对
   留在私有实验，不能作为公开 CI 的输入。Windows 虚拟 runner 只能证明对应设备/权限，
   不能代表实体机或所有控制器。默认接线前还需同进程启动与 COM/音频共存检查。
5. 只有在已核对的范围内才考虑接入。保留以下用例：超时/迟到不落盘、已有 ID 优先、
   首次空种子拒绝、事务失败不轮换、账号凭据 deviceId 不变。分支没实测就保留缺口，
   不通过真实账号请求来弥补采集证据，也不把 CI 编译成功记为官方等价。

当前没有 Windows 硬件采集或生产接线。已有仅处理合成字符串的独立探针，见下节。

7. Windows 代码页与主板过滤离线探针

`scripts/research/windows_identity_encoding_probe.rs` 没有外部依赖，不启动桌面、COM、
WMI，不读硬件/注册表/账号，不接收参数，不更改系统或线程的 locale。它调用：

- GetACP、GetCPInfoExW(CP_ACP / CP_THREAD_ACP)：报告 OS 返回的编号与最大字符宽度；
  用同一固定字节串对照别名和显式编号，不假设两者相同。
- WideCharToMultiByte(CP_ACP, 0)：生成固定 Unicode 字符串的窄字节；再分别用两个
  代码页别名解码。另用固定 CP1252、CP936、UTF-8 和坏 UTF-8 字节作为对照。
- MultiByteToWideChar：并列记录 `-1` 输入的完整目标、`-1` 输入的短一单元目标，
  以及显式非 NUL 输入长度配合同样短目标。`short` 行包括返回值、立即读出的
  GetLastError、改写单元数及目标内容，保留人工添加 NUL 之前的观察。API 返回失败
  但仍写入部分内容也是有效观察。空内容走早退；缓冲区前后哨兵必须完整。
- 用 Windows UCRT 的 `iswctype(0x4)`、`_wcslwr_s` 检查上述主板过滤规则；冻结
  ASCII 序列的空格、原大小写、占位词、全数字和长度边界，额外报告合成的非 ASCII
  数字分类。探针不从成功的完整缓冲区输出推断官方短缓冲区一定可用。

在仓库根目录用已固定工具链的 Windows x64 PowerShell 运行：

    New-Item -ItemType Directory -Force .build/windows-identity-encoding | Out-Null
    rustc --edition 2024 -D warnings scripts/research/windows_identity_encoding_probe.rs -o .build/windows-identity-encoding/probe.exe
    if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
    & .build/windows-identity-encoding/probe.exe
    if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }

可另编一个带本探针专用 UTF-8 manifest 的 MSVC 可执行文件，不改全局代码页：

    rustc --edition 2024 -D warnings -C link-arg=/MANIFEST:EMBED -C link-arg=/MANIFESTINPUT:scripts/research/windows_identity_encoding_utf8.manifest scripts/research/windows_identity_encoding_probe.rs -o .build/windows-identity-encoding/probe-utf8.exe
    if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
    & .build/windows-identity-encoding/probe-utf8.exe
    if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }

第二个程序必须实际报告 GetACP=65001 才计为 UTF-8 ACP 证据。显式 CP65001 对照并不
等于进程 ACP 为 UTF-8。两次都只保留合成输入观察；`encoding_probe=complete` 只说明
探针断言通过，不等同于硬件采集、官方二进制对照或生产接线已验证。

本地 Linux 用 Rust 1.96.0 / x86_64-pc-windows-gnu 交叉链接并核对 PE 导入，纯合成
UTF-16 规则通过 2 项测试。未在本机执行 Windows API；短缓冲区、别名与 UTF-8
manifest 的运行观察仍等 Windows。Windows Native CI 运行上面的首个程序，输出只含
合成样本及代码页结果；
它不需要解包材料、账号、网络、音频设备或桌面会话。
