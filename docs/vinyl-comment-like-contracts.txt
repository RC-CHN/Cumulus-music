Cumulus 只在签名验证过 PH-PC-optimizeComment=t1、同账号、当前
Catalog 播放的标准内嵌评论版面显示控制。渲染端只传 epoch、playId、
规范数字评论 id 与 set(desired) 或 reconcile，不传歌曲、线程、账号或
凭据。原生由实际已发布播放器状态推导 R_SO_4_{id}；先读取该线程的
指定评论（同绑定的 /api/v1/resource/comments/{threadId}，limit=1、
offset=0、beforeTime=0，指定 commentId；其它标记沿用 false），
要求存在、可用、无明确冲突线程且 liked 是已知布尔，已满足目标时不发送。
固定类型的请求与发布/回复共用同一 HTTP 锁、签名凭据版本、Cookie
作用域匹配和临发送播放状态检查，不回退到通用评论发送接口。

在当前账号的 comment-likes-v1 中，按账号、线程和评论互斥地持久化
Sending。已证实发送前中止时恢复先前记录或移除这条未发送意图；若
可能调用过后端且结果不明，则保留不确定记录。变更接口确认后仍使用
既有的两次一致目标回读；只有已确认的 liked/count 才投影到 Hot 和
Latest 的同 ID 卡片。旧的追加读不覆盖这次投影，未推进其 offset。
不确定时禁用点赞/取消点赞并显示「核对点赞状态」；该按钮只读，
也可在独立评论页核对同一条记录。不自动重发；账号或歌曲切换后丢弃
旧显示回执。共享评论缓存使用既有写操作版本，独立评论页的请求不变。
这是故意比官方更谨慎的确认和恢复流程。举报、删除和分享未加入此批。

真实桌面合成证据
----------------

scripts/ci/vinyl_comments_smoke.py --likes 在隔离的 Linux WebKitGTK 与
libmpv 上验证四态：初始未赞、点赞已确认、取消回包丢失、显式读回确认。
精彩与最新的同一条评论共享已确认的计数和选中态；未决期间保留旧值并提示
核对，禁止重发。只读确认不把本机日志的未收到回执改成已收到。原生播放
实例、队列、暂停位置和非零滚动都保持不变；没有使用真实账号发送点赞。
独立复验旧读取 7 态与编辑器 11 态；Windows 实窗结果由对应 CI 提供。
