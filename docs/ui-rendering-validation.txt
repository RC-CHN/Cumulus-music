Desktop rendering and window controls — 2026-10-27

Scope
The main window is frameless on Linux/Windows. Search, account and native window
controls share the existing application header. Empty header space is a native
drag region, with double-click maximize/restore. Eight narrow edge/corner hit
regions dispatch native resize drags. Closing still goes through Tauri's ordinary
close event and the existing Together cleanup coordinator.

Scrolling
TrackTable and QueuePanel share a bounded, buffered visible-row window. Passive
scroll events schedule at most one range calculation per animation frame; movement
inside the safety buffer does not publish another Vue update. Row memoization
retains unchanged rows. Zebra colors use absolute row indices, so scrolling no
longer flips the color of every retained row when the buffer advances. Resize,
queue shrink, empty lists and jump/reverse scrolling are covered. Artwork in a
40px track row requests a 120px public CDN thumbnail (up to 3x density), decodes
asynchronously, and retains native lazy loading. No authorized media URL enters
this image path.

The page tree depends on stable current song/local/voice identifiers. Playback
clock changes remain in the player and lyric components, rather than re-rendering
the library and sidebar. Playlist counts no longer use hundreds of backdrop blur
filters. No permanent requestAnimationFrame loop runs while the application idles.

Motion
Pages use short fade/vertical transitions; queue and lyrics panels slide/fade;
modal dialogs fade/scale; login methods fade/slide; navigation and window controls
have short state feedback. Only transform/opacity are animated for moving content.
The lyric panel leaves the custom window header accessible. Native dialog focus
restoration waits until the leave animation removes the modal from the top layer.
Switching modals retains the original page focus target. Reduced-motion preference
removes movement and transition delays.

Linux GPU behavior
WebKitGTK requests Always acceleration and smooth scrolling. The optional public
PreferPageRenderingUpdatesNear60FPS feature is disabled when present, without
inventing a JavaScript timer to force refresh. WebView2 keeps its normal GPU default.

On this machine: Ubuntu 26.04.1, WebKitGTK 2.52.6, KDE Wayland, NVIDIA RTX 3090,
driver 595.99.02, physical monitor 143.999 Hz, GTK device scale 2. The distribution's
NVIDIA DMA-BUF patch makes the acceleration policy read back as Never even after
requesting Always. Forcing DMA-BUF alone reproduces a Wayland disconnect:
  explicit sync is used, but no acquire point is set
NVIDIA's __NV_DISABLE_EXPLICIT_SYNC=1 fixes that incompatibility while retaining
GPU buffer transport. A shared-memory GPU presentation experiment also worked but
was slower in this workload, so it is a fallback, not the Wayland default.

Before GTK or worker startup, auto mode detects NVIDIA via DRM driver links and
sets process-local defaults only when the user has not supplied that variable:
- NVIDIA + Wayland: WEBKIT_FORCE_DMABUF_RENDERER=1,
  __NV_DISABLE_EXPLICIT_SYNC=1.
- NVIDIA + X11: GPU shared-memory transport (the Wayland setting is inapplicable).
- Other drivers: normal hardware-acceleration initialization.
CUMULUS_RENDERER=software explicitly selects software rendering;
CUMULUS_RENDERER=gpu-shm selects GPU/shared-memory transport;
CUMULUS_RENDERER=gpu requests the direct path without auto driver workarounds.
No desktop-wide, driver, display-frequency or login-session setting is modified.
The startup environment API is unsafe with a documented before-threads contract;
the WebKit feature FFI is isolated to the GTK thread with a bounded list lifetime.
The Linux package requires WebKitGTK >= 2.42 for those public feature APIs.

Automatic startup recovery
The shipped desktop executable now validates graphics BEFORE GTK/main-client,
account, player or background-business initialization. A separate, bounded child
shows a small local Cumulus splash using the real WebView. It requires DOM layout,
at least 12 animation frames over 400ms, and on Linux a WebKit snapshot containing
the colored logo (an empty/black surface does not pass). There are no music API
commands, session reads or online resources in this child. The visible splash has
a cancel action; cancelling stops recovery rather than opening another window.
The splash also honors reduced motion. A real GTK/WebKit check with animations
disabled confirmed the media query matched and the logo's translation stayed zero.

Auto mode tries each candidate once: normal GPU configuration, then GPU/SHM on
Linux, then software. Windows uses WebView2's normal renderer, then --disable-gpu
as a compatibility fallback. Explicit CUMULUS_RENDERER choices remain pinned for
advanced diagnosis. Each child has a 15-second deadline; success requires BOTH a
successful exit and a render acknowledgement in its private temporary directory.
A hung/failed check never causes the full music client to restart or retry writes.
Linux timeout cleanup targets the check's own process group; Windows uses a
kill-on-close job assigned before the child can create WebView2 workers.
If every candidate fails, one native error dialog is shown without starting any
account/business work. This is startup recovery, not automatic restart after an
arbitrary crash later during playback or a user mutation.

The last working auto profile is stored atomically in the local renderer cache.
It is rechecked on each launch, with lower candidates available if it has broken.
Known-bad higher candidates are skipped until the seven-day retry period expires
or the environment changes. The period does not extend on every successful launch.
Cache invalidation includes the executable, display/backend overrides and on Linux
WebKit version, kernel/driver version and GPU model; Windows includes WebView2's
version. Windows driver changes are caught by the mandatory check, but recovery to
a faster profile after a driver repair may wait for the seven-day retry period.
The stored environment key is a local hash, not a serial number or server identity.
Missing, malformed, oversized or unwritable cache never prevents renderer checks.

Validation of recovery
On the physical NVIDIA/Wayland machine, explicitly restoring the broken sync
behavior (__NV_DISABLE_EXPLICIT_SYNC=0) made the default check fail. The same
launch then selected gpu-shm successfully. The next launch started at cached
gpu-shm and succeeded in one attempt. Separate default and software checks passed.
Local synthetic evidence: .build/graphics-recovery-first.json,
.build/graphics-recovery-cached.json and .build/graphics-smoke-local.json.
The startup diagnostic creates no SQLite account/business databases.
Unit tests cover crash/timeout progression, all-candidate exhaustion, cancellation,
manual overrides, changed environment/expiry/corruption, exit without render ack,
and killing a hung child. CI runs the shipped binary's graphics diagnostic for
default, cached and software paths on both supported platforms, plus Linux SHM.
Windows does not yet perform the Linux pixel snapshot check; its acknowledgement
covers mapped-page layout and animation frames. Virtual-runner results do not
establish physical GPU compatibility on every driver.

WebView2's browser flags are a compatibility mechanism with runtime-version risk,
not a permanent API guarantee. The fallback is checked on every launch and the
normal mode adds no flags. Relevant API references:
https://webkitgtk.org/reference/webkit2gtk/stable/method.WebView.get_snapshot.html
https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/webview-features-flags

Evidence and limits
The standalone scroll_ui_probe renders the production frontend and IPC using
2,000 synthetic songs and 300 synthetic playlists, without an account or music
network traffic. It records requestAnimationFrame intervals during idle, song
scrolling and playlist scrolling, verifies bounded song DOM, jumps/reverse/end
positions, page navigation, native-dialog open/close and focus, and custom chrome.
Physical-monitor frame rates are diagnostics, not CI gates on virtual runners.
Local manual mode verifies native maximize/restore/close. A temporary KWin
observer independently confirmed minimized=true after the custom minimize button;
GTK/Wayland is_minimized returned false, so its ICONIFIED getter is not used as
proof. The observer was unloaded after the test. CI uses
embedded frontend assets; an explicitly selected dist snapshot exists only in
this standalone probe for manual comparisons, never in the shipped application.

The software baseline without cover images already reached about 62 FPS. It is
not evidence that the user's image-heavy real library was smooth. The direct GPU
compatibility run measured 59.7 FPS for songs and 60.0 FPS for playlists, with
p95 intervals of 18ms; the shared-memory run measured about 51/54 FPS. These are
short local runs on this machine, not a universal 60 FPS guarantee or proof of
144 FPS. Different GPUs, actual covers, server latency, long sessions and desktop
load can change results. The current acceptance target is stable approximately
60 FPS, as requested; the physical monitor itself is not limited to 60 Hz.
