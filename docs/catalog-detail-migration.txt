ArtistApi 请求
detail       /api/artist/v3/detail        id,top=50,e_r=false；nginxCache=true
dynamic      /api/artist/detail/dynamic   id；收藏状态与演出数量独立读取
albums       /api/artist/albums/{id}      limit,offset
songs        /api/v2/artist/songs         id,limit,offset
introduction /api/artist/introduction     id
similar      /api/discovery/simiArtist    artistid,limit,offset,total=true
videos       /api/mlog/artist/video       artistId,tab=1,order=0,page
concerts     /api/concert/list/byartist   artistId,limit,offset

除 detail 外不强行启用 nginxCache；官方客户端自己的缓存策略不等同于请求头缓存选项。
歌曲接口传给官方格式化器的 uid 是本地归一化上下文，不发送为 HTTP 字段。
相似歌手使用小写 artistid；视频 page 为 JSON 字符串，其 cursor 是十进制数字。
视频游标不经过 JavaScript 数值或 Rust u64/f64 缩窄，保留十进制内容。
官方默认 limit=20、offset=0；本实现增加 limit 1..100、offset <=1,000,000、
游标最长128位的客户端输入边界。这些上限是本实现的约束，不冒称官方服务端上限。
所有请求只接受成功状态 200；服务错误继续走现有 Api 错误处理，不伪装空页。

第二阶段：原生页面快照与权益合并
core/src/catalog/details/{query,request,service}.rs 提供 CatalogQuery、CatalogDetails 和
SavedCatalogPage。查询覆盖歌手热门、独立动态状态、分页歌曲/专辑/相似歌手/视频/演出、
简介与专辑详情。SavedCatalogPage.response 是原生元数据，不能直接作为 IPC DTO。

page_for 的顺序：
  校验 ID/分页 -> 绑定账号代次 -> 按账号和完整查询互斥 -> 官方读取 ->
  校验响应身份与必要字段/合并权益 -> 再次核验账号 -> 持久化 -> 返回。
缓存键含查询种类、资源 ID、页码/游标及大小；StateStore owner 使用当前账号。
cached_for 校验缓存的查询身份、响应结构和 revision；没有记录返回 None，不冒充空页。
读取失败、返回另一歌手、动态状态缺少 followed、账号切换后的迟到响应均不覆盖已有快照。
歌曲 revision 包含查询及有序 ID，权益刷新不改变队列顺序 revision。
视频声明 more=true 却返回同一数字游标（包括前导零等价形式）时拒绝该页，保留旧快照。

官方 M/15 的 g={enable:false}（1012 行）。本地快照是额外的恢复能力，page_for 每次均联网；
没有引入“缓存三小时内直接成功”的逻辑。前端接线时仍须显式刷新，快照不能授予播放权益。
M/612 的热门歌曲先读详情，再调用 M/15 Dg：/api/song/enhance/privilege，
ids 是 JSON 字符串，默认省略 trialMode；M/15 对照中的 MV 路径显式传 -1。
新 CatalogApi.privileges 保留输入/输出顺序与重复项，按500项分批、最多50000项；
分批和数量上限是本实现约束，不宣称它们来自官方 Dg。

合并按 M/21 B（21.js 683 行附近）恢复：
- 同 ID 权益取最后一次值；未返回权益的原歌曲去除旧 privilege，保持未知。
- 仅在权益条目数大于原歌曲数时，对原列表中没有的 ID 按权益回复顺序补入资料缺失条目。
- 补入条目保留 id/privilege/空 artists；不捏造名称或把它视为已完整读取歌曲资料。
- 原始 ID 集合不会随补入更新，因此重复的额外权益 ID 保持重复，未自行排序或去重。
M/21 R 的 id || albumId 也用于专辑列表、详情校验及歌曲专辑引用，保留大整数字符串。

这一阶段没有复用 MV 域已有的严格权益字典：官方歌手合并需要保留原始顺序及补入分支。
M/21 V 同时处理 base.type=2 的视频与 type=3/isMv 的 MV；前端尚未接线，不能把每个
返回条目或所有数字 ID 当作 MV。相关分流、播放及真实接口验收仍是后续工作。
