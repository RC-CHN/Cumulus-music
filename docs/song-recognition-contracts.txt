2. 指纹及原生 EAPI

- 313F40 从任务缓冲取数据，313FD8–313FDB 将字节数除以 2。
  315270 仅清零 8 字节本地对象，实际构造为 D0A2C0，D0A450 复位，
  D0A3B0 接收输入指针和样本数，D0A430 抽取结果向量。空向量在 31406D
  返回 -6。D0A9C0 → D10000 将有符号 16 位样本按 1/32768 转为 f32，
  再交给 D0CA30；指纹提取继续执行 D10660、D0AA80 等内部代码。

  EC7922 → 33D450 写全局对象 +0x130；315330 返回该字段；

完整官方指纹对照（Linux x86_64，合成样本，无网络）

使用 Unicorn 2.1.4，按整 DLL SHA 验证后，仅在代码和数据权限受限的客体执行
D0A2C0 → D0A450 → D0A3B0 → D0A430。用基本块白名单禁止未知执行；每次
调用最多 250,000,000 条指令及 30 秒，客体临时内存 32 MiB。实际信号运算、
排序、二进制写包、原生 zlib 与 AES 都执行官方指令。替身限于有界
malloc/calloc/free/memset/memcpy、平衡的单线程 CRT 锁、一个固定清理回调
登记及固定 C locale 的 CRT 线程状态。C locale 表来自 DLL 219B328 指向的
219B1D0/219B3A0，C 字符串为 219B338；仅允许经过核对的少量全局写入。
Windows 导入不加载；未启动 DLL、不映射音频设备、不创建套接字。
D0C0F0 的原始 UCRT count/write 分支也执行：输入 3.90625、100、4000、1
得到 3.906250、100.000000、4000.000000、1.000000 的 ASCII 加 NUL。

三组都是 8,000 Hz、24,000 个单声道有符号小端 i16。每组用两个独立新进程
从构造开始执行，完整输出逐字节一致，输出向量 begin/end/capacity 与所有权
已检查。two-tone、整数 xorshift 噪声、静音分别输出 160/864/32 字节，
打包明文为 237/1293/33 字节，压缩流为 156/859/21 字节。静音仍可产生
非空包，不能将“静音”“没有命中”与“空指纹”合并。
core/tests/fixtures/song-recognition-official.json 冻结样本生成配方、PCM
SHA256、原始 packed 字节、官方 zlib 字节、最终 Base64 和各层摘要。
fixture SHA256 1fa1f7be24c9d1632a2b9d3cfb319067370becd15d60769623574f11a9d107a4。
内容都是合成字节；官方 DLL、映像和对照程序不入库。

封包的三层边界已单独核对：
- D0AA80 中的 D0C5A0/D0F4C0 写二进制字段，D0D770/D0CFD0 走原生
  zlib 1.2.5（版本字符串 RVA 1A065F0，D0D045 → BFDED0）。
  deflateInit 使用 level=-1（默认）、窗口 15、内存级别 8、策略 0。
  对三组官方压缩流解压均得到对应 packed 字节，系统 Python 的 zlib 1.3.1
  对同三组 packed 字节重压也相同；只证明这些向量，不是所有后端的
  通用字节等价。后续用 Rust 比较压缩差异，不混入 AES 对照。
- D0ADE0 从 219B938 → 1BA1248 取十六个 ASCII 字符 074B97221F27F029；
  D0AEFF–D0AFD3 两次将首字节移到尾部，实际 AES-128 key 为
  4B97221F27F02907。这是固定二进制常量，不来自账号、设备或 EAPI 的 key。
  D10280 仅对非空输入按 PKCS#7 填充，每 16 字节独立交 D15C20，
  使用 AES S 盒（1BA1440），没有 IV；空输入返回空向量。
  已在 D10280 入口仅观察合成输入的压缩流和 key，OpenSSL 的
  AES-128-ECB/PKCS#7 对三组都生成完全相同的最终字节。
- 314B58 的标准 Base64 在上述 AES 输出之后；EAPI 是外层独立签名/加密。
  冻结的 rawdata 是该 Base64，不含请求 Cookie、会话或任何真人样本。
