发布与 CI/CD

支持矩阵：Linux x86_64（Ubuntu 24.04 基线）、Windows x86_64（MSVC）。用户明确排除 macOS。
规则的权威入口是根目录 AGENTS.md。待发布版本以 Cargo.toml 的 workspace.package.version
为准；发布检查会核对 Cargo.lock、前端及 Tauri 版本文件和对应发行说明。

CI (.github/workflows/ci.yml)
1. 独立前端 runner：公开源文件边界、版本与 release 历史、发布门禁的拒绝分支测试、格式、前端测试、类型检查和正式构建。
2. Linux/Windows 原生检查 runner 并行执行 fmt、严格 Clippy 和锁定的全工作区测试（包括 examples 编译）。Linux/Windows 发行构建各用另一个独立 runner，与原生检查并行；从同一提交和锁定工具链构建，运行已安装包或解包产物验证。
3. Linux 的本机媒体 WebView job 从同一次 CI 的打包 job 核对实际滤镜和 FLAC。
   下载、搜索、播放器回归另用 Linux runner，只等前端和共用探针构建。
   两组核对同提交、run/attempt 的探针及前端资源摘要；本机媒体组的包来源检查保留。
   Windows 打包 job 保留安装包、便携 ZIP、冷 FLAC、自然结束、设置及依赖 MSYS2
   测试用编码器的本地队列验收；其余原生和 WebView2 探针分为 playback、search-account、
   catalog 三个 Windows runner。每个 runner 内的桌面检查串行；一组失败不取消另两组。
   各组校验并解包同提交、同 run/attempt 的 Windows 便携 ZIP，沿用包内 PE、DLL 和
   固定 FLAC 闭包。Windows 打包 job 的前端 dist 和已编译 ux_ui_probe 同样经该
   attempt 的清单和文件 SHA-256 核对后复用，其余示例在各组用锁定工具链编译。
   仅重跑失败组不能借用较早 attempt 的运行库；需重跑所有 job。
   两端在真实桌面初始化后运行原生媒体测试；Linux 强制使用 en_US.UTF-8，检查 GTK 数字 locale 冲突及保留界面语言。Linux 另运行真实 FFmpeg LADSPA 音效链和 WebKitGTK 登录失效/重新登录 UI 截图测试。Windows 在真实 WebView2 中验证相同生产 UI/IPC 的 DOM 状态、凭据失效及旧策略队列清理；不声称有 Windows 截图验证。两端 UI 均只使用合成 HTTP。
4. CI gate 同时要求前端、两端原生检查、两端发行打包、Linux 共用探针和两组
   WebView、Windows 三组 WebView 全部成功。失败/取消/跳过均不能发布；CD 独立核对各 job 名称。
   两端还运行长列表/自定义窗口、启动渲染自动回退及 29 项主题/菜单/弹窗/重启记忆的实际 WebView 检查。
5. 输出 packages-linux-x64 / packages-windows-x64 两组产物，包含包、精确提交/CI run/attempt/大小/SHA256 清单。保留 14 天。
研究用官方 JS 对照生成脚本要求忽略的 references；公开 CI 使用已提交的合成冻结向量，不假装在 runner 上重新执行了不存在的原始材料。
CI 不导入账号 Cookie、不调用真实账号写接口。libmpv null 输出只证明解码与控制，不能代替真机声卡测试。

打包
python scripts/ci/package.py --platform linux-x64 或 windows-x64，必须在对应系统运行。
发行构建要求工作区干净，构建结束再次核对 HEAD/工作区，禁止把中途修改的内容归给旧提交。
先 npm --prefix frontend ci 与 npm --prefix frontend run build。
Windows 还需 CUMULUS_MSYS2_ROOT 指向装有 UCRT64 mpv/binutils 的 MSYS2 根目录。
Windows 按 libmpv/ffprobe 的 PE 导入表递归收集 DLL；实际解码和本地库元数据读取测试清除 PATH 中的 MSYS2，避免漏装依赖被 runner 掩盖。
Linux .deb 声明 libmpv2/WebKitGTK/FFmpeg 等系统依赖；tar.gz 也需要这些系统依赖。
Windows 提供 NSIS/zip，附原生运行时依赖、上游许可证与包版本来源。没有签名证书，不声称已签名。
主线 Windows 发行运行时使用启用 LADSPA 的固定 FFmpeg 配方。两平台
打包均须通过实际 libmpv → LADSPA → C DSP 回归。独立 PEQ 探针用 44.1/96 kHz
双声道合成源核对处理进度、原生版本、无失败块；清单写入 parametricPlayback，
CD 必须核对本次结果。这是原生组件验证，不代表桌面提供完整预设或实机听感。
当前配置不改变已发布包的边界。
Linux 打包 job 按本次 manifest 校验 .deb 和便携 tar.gz，分别在私有
目录和无外网 Xvfb 中启动包内程序。两条路径均经正式界面导入合成
FLAC、选择均衡器预设、暂停，并在私有 PipeWire 空输出检查音频样本。
便携程序优先加载与自己相邻的滤镜，避免选中另一个已安装版本的库。
此项覆盖包内程序与软件输出，不替代原生格式探针或实体声卡验收。
打包脚本的生成目录必须不存在；重试前仅清理 .build/package-stage/<platform>、.build/packages/<platform> 中对应的失败构建，保留需要调查的证据。

发布顺序
1. 完成所有实现/配置/发行说明，更新 Cargo.toml、Cargo.lock、frontend/package*.json、desktop/tauri.conf.json，推送普通功能/修复提交，等待 CI 全绿。
2. 创建唯一、内容树不变的标记提交：git commit --allow-empty -m 'chore:release X.Y.Z'。
   git push origin main。不要提前打 tag。普通修改必须在该提交之前准备好。
3. 等待该标记提交自己的 CI 全绿，取得其 run ID。
4. gh workflow run release.yml --ref main -f version=X.Y.Z -f ci_run_id=<ID>。
5. CD 验证唯一 release commit、版本一致、main push CI、精确 SHA、run attempt、产物集合与校验和。
   它核对前端、两端原生检查、Linux 共用探针和两组 WebView、Windows 三组 WebView
   与 CI gate；gate 还要求两端打包成功。
   只下载此 CI 的产物，不重新构建。创建指向该 commit 的 vX.Y.Z 标签；先草稿上传完整附件，再公开。
6. 检查 Release URL、所有附件、SHA256SUMS、release-provenance.json 和 tag 目标。
用户要求 RC 时，上述标记标题、version 输入和 tag 使用完整的 X.Y.Z-rc.N（N 为正整数）；
GitHub 将其标记为预发布，不更新最新正式版。

失败处理
- CI 未过：修复后重新验证，不打 tag/不发版本。标记提交只在内容全部准备完成后创建，避免同版本多条 release commit。
- release commit 上若出现真实代码问题，不能再追加同版本 release commit；保留失败记录并推进下一版本，禁止改写已公开历史。
- tag/Release 已存在：CD 拒绝覆盖。草稿恢复只接受原标签、原草稿及与 CI 清单完全一致的已上传附件；缺失附件或摘要不符时拒绝。恢复不会上传或覆盖附件，详见 release-recovery.txt。
- CI 正在 rerun/attempt 改变/附件过期/摘要不符：停止发布，等待完整、同一 attempt 的成功 CI 产物。
- GitHub 的 contents:write 权限只授予 CD 发布 job；PR CI 只有读取权限，不运行来自 fork 的代码来发布。
