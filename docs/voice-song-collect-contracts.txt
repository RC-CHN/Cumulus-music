Native Cumulus scope

- Core prepare freezes two to 100 ordered unique indices from the current
  native episode shelf. No renderer track IDs. It returns eligible count,
  omitted indices, and whether the first-row fallback was used. It keeps the
  first occurrence if the card duplicates a canonical song ID. Unknown
  privilege forms, mismatched privilege IDs, and local/cloud/alternate
  identity are omitted; omitting one cannot promote an otherwise skipped
  first item. An empty result issues no receipt.
- Destination pages are fetched only on explicit use of the selection,
  carry the same signed PC account/card revision, and admit only observed
  regular owned IDs. Refreshing a page revokes its old observations and a
  late same-page response cannot restore them. Native fetches exact detail
  and rechecks ID, regular ownership, and absence of local-only entries
  before a single guarded add. No writes on opening or listing the picker.
- Account generation, native API, unique URL-scoped account cookie
  identity, current episode/play ID, shelf receipt and transport credential
  revision are rechecked through dispatch. An ambiguous response stays in
  the account's shared durable playlist journal. The same choice returns
  that operation; readback checks it and never sends another add. A lost
  shelf/selection cannot reconcile through this action; the general playlist
  journal still holds it for the same account. A proved existing membership
  can be Unchanged without a duplicate add; readback proves exact resulting
  membership and prior-item order, not server insertion position.
- Desktop uses four typed commands: prepare, read destination page, add to
  observed destination, and read/reconcile the same operation. The renderer
  sends card and selection receipts plus displayed indices; no raw song ID
  can be selected for the write. The modal has default/recently tabs,
  loading/empty/error and waiting states, an explicit “核对结果” action,
  and returns focus to the originating episode row. Ordinary tracks keep
  their existing independent menu and single-track action.
- The Linux sealed WebKitGTK proof drives the group menu with trusted
  pointer input: four selected, three eligible in selection order, one
  blocked by collection privilege, one ordinary owned destination, zero
  writes after cancellation, and one lost-reply add confirmed by readback.
  The paused libmpv instance, clock and queue remain the same through all
  thirteen stages; no real service access or account writes. Ctrl+S
  enters the same workflow from a focused selected row; Windows desktop
  gestures and real-account rights were not verified in this proof.

Native system-liked destination

- M/3160:923–930,957–977 uses the first numeric specialType=5 from the host
  playlist list for starPlaylistId. M/232:229–263 and M/15:1315–1328 show
  /api/user/playlist with uid, limit 1000 and offset in steps of 1000, plus a
  separate pinned overlay. M/3160:1141–1142,1227–1231,1241–1254 compares the
  chosen ID to this star, sends the same ordered batch add, and updates liked
  IDs and its notice. It does not issue individual heart requests.
- The native picker reads its optional system-liked row separately from the
  regular sorted pages. `player_voice_songs_collect_liked_destination` takes
  the same account/play/card/selection target and returns account-scoped
  `{playlistId,destinationReceipt}` or null. It checks an unpinned, complete
  host list (maximum ten pages; foreign, duplicate or ambiguous stars fail
  closed) and a fresh exact detail with agreeing account ownership, numeric
  specialType=5 and no local-only entries. It never reads liked IDs or writes.
  A successful list with no star returns null. Reloading the row revokes the
  older receipt even when the playlist ID did not change.
- A future picker can load this row once for the current selection alongside
  the regular list, without rereading it for each page or sort. Only a non-null
  verified row enables its system-liked action. Use its playlistId for display
  identity and to check the result; send only destinationReceipt with the
  selection target to `player_voice_songs_collect_liked`. A changed star fails
  before write rather than retargeting the selection. The independent regular
  picker and generic editor still do not permit system playlists.
- M/3160:990–1028, M/232:310–329 and M/15:1409–1414 independently describe
  refresh of the star's detail trackIds and a native local-only overlay. For
  confirmation Cumulus requires both the complete star detail and its existing
  account-liked membership read (/api/song/like/get {uid}), not the official
  optimistic update or a copy of the input. Same native PC account, Cookie,
  device and credential revision must cover list, detail, membership, card
  and the guarded write. If the two preflight sources disagree for any
  selected ID, no write occurs. Only verified confirmation publishes the
  observed liked IDs into the account resource cache.
- The existing playlist journal records a system-liked marker before the
  single possible batch write. A 200 reply or matching playlist detail alone
  cannot settle it. Pending operations require the same current system star
  and independently observed membership on readback. The shared journal can
  read back an interrupted operation after a new session opens the same
  account and database, even when the original episode receipt is gone. It
  never sends the batch again. Main-window typed desktop bridge only in this
  slice; no UI wiring or live account writes.
